## 两条上山的路

同一道 g12，两种解法殊途同归：

- **重炮路**：召回 50 + cross-encoder 全池精排——不改问题，用算力把"小洞==气孔"
  的对应关系在排序阶段算出来。延迟 3.1s/题（本地 CPU），零 API 成本。
- **翻译路**：先花一次 LLM 调用把"黑色火山石头上的小洞"翻译成"玄武岩 气孔构造"，
  然后 0.3ms 的词法检索直接命中。API 成本约 ¥0.15/题，总延迟由 LLM 调用主导（数秒）。

**病在查询就治查询。** 改写在根上解决问题（把用户的话翻译成资料的话），
因此它与检索方式无关——最便宜的 BM25 也能受益，且可与精排叠加。

## 三条设计纪律（都有前科可循）

1. **原始问题永远保留为第一路**——改写可能改错，新机制只许扩大召回，不许有否决权
   （与 Day 3 单路保底名额同源）。
2. **精排/回答仍以原始问题为准**——HyDE 的假想答案只用于检索，是钓饵不是证据。
3. **--compare 下改写按题缓存**——四种配置共用同一份改写，控制变量且省钱。

## 局限如实记录

- 延迟：7.6s/题（含 Agent SDK 会话开销与 LLM 调用），交互场景需预热连接或换轻量端点。
- 改写本身不可确定性校验（它是 LLM 输出）；防线是"原问题保底"而非校验改写质量。
